# Zipf-exponent sweep (Figure 3, column 1)

Cloak allocates its per-batch budgets assuming the input follows a Zipf
distribution over reuse distances with exponent s = 1.0. This experiment keeps
that assumption fixed and varies the *actual* skew of the input workload from
s = 0.0 (uniform) to s = 2.0, showing how throughput, latency and batch
utilization depend on how well the anticipated and the real distribution match.

Paper: Section 7.2.2 "Effect of workload skew", Figure 3 first column
(throughput, mean/p99 latency, batch utilization vs. Zipf exponent).

## Parameter grid

All runs use [`configs/zipf-exponent.toml`](configs/zipf-exponent.toml)
(N = 10^6 elements of 1 KB, batch size 4,000 = first-set budget 433, cache
1,000 entries, queue capacity 2x batch size, 20 ms batching interval, 16
threads). Per run, `run.sh` passes the workload and `--client-req-per-sec`.
The client rate is a target close to the maximum Cloak sustains for each
workload, as used for the paper.

| label  | workload             | input Zipf s | client rate (req/s) |
|--------|----------------------|-------------:|--------------------:|
| `s0.0` | `workloads/s0.0.xz`  | 0.0 | 30,000  |
| `s0.1` | `workloads/s0.1.xz`  | 0.1 | 33,000  |
| `s0.2` | `workloads/s0.2.xz`  | 0.2 | 34,000  |
| `s0.3` | `workloads/s0.3.xz`  | 0.3 | 36,000  |
| `s0.4` | `workloads/s0.4.xz`  | 0.4 | 40,000  |
| `s0.5` | `workloads/s0.5.xz`  | 0.5 | 44,000  |
| `s0.6` | `workloads/s0.6.xz`  | 0.6 | 50,000  |
| `s0.7` | `workloads/s0.7.xz`  | 0.7 | 56,000  |
| `s0.8` | `workloads/s0.8.xz`  | 0.8 | 76,000  |
| `s0.9` | `workloads/s0.9.xz`  | 0.9 | 104,000 |

21 configurations x 5 repetitions = 105 runs. Repetitions are the outer loop
(all 21 workloads, then the next repetition), as in the paper.

## Workloads

`workloads/s<X>.xz` (xz-compressed, decompressed once into `.cache/` by the
harness): 1,000,000 requests over 10^6 keys, 50% writes. Each line is a read
(`key`) or a write (`key value`). They were generated by repeatedly sampling a
reuse distance from a Zipf distribution with exponent s and querying the key
whose current reuse distance equals the sample (paper Section 7.1).
`target/release/gen_workload` implements this generator; the shipped files are
the exact ones used for the paper (a regenerated sweep differs by its random
seed). `s1.0.xz` is also the input of the batch-size, cache-size and
element-size sweeps, whose `run.sh` scripts read it from this folder.

## Running

Prerequisites: a deployed cluster (`ansible/inventory` + `ansible/deploy.yml`,
see the top-level README), or a local build for `LOCAL=1`.

```sh
cd experiments/zipf-exponent
./run.sh                          # full sweep: 5 repetitions on the cluster
SMOKE=1 ./run.sh                  # 1 repetition, first 200,000 requests of each workload
ONLY='^s(0\.0|1\.0|2\.0)$' ./run.sh   # a subset of the labels
LOCAL=1 SMOKE=1 ONLY='^s1\.0$' ./run.sh   # on this machine (server needs ~1.1 GB RAM)
DRY_RUN=1 ./run.sh                # print the commands only
```

All harness variables (`REPS`, `RESULTS_DIR`, `INVENTORY`, `VERBOSE`, ...) are
described in [`../README.md`](../README.md#harness-variables).

**Expected runtime** on the paper's hardware (3x AWS m6a.4xlarge, 16 vCPU /
64 GB): the client phase of one repetition takes about 5 minutes in total
(1M requests at the achieved throughput: ~34 s for s = 0.0, ~7 s for s >= 1.0),
plus about 20 s of fixed cost per run (Ansible orchestration, server start,
storage initialization by the proxy; more with a remote controller). One
repetition is ~12 min, the full 5-repetition sweep ~1 hour. `SMOKE=1` takes
~8 min (the fixed cost dominates).

## Results and plotting

Results go to `results/<label>-stats.csv` and `results/<label>-ratio.csv`
(`results-smoke/` with `SMOKE=1`), one row per repetition; the columns are
described in [`../README.md`](../README.md#result-files). `paper-results/`
holds the 5 repetitions behind Figure 3 in the same format. From the
repository root, `uv run python plots/fig3_ablations.py` draws Figure 3 from
`results/` (`--paper`, `--smoke` and `--results-root` select other data; see
[`../README.md`](../README.md#plotting)).
